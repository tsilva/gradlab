# Upload Checkpoint

Operate the repository's Publication services. `PlayerPublicationService` and
`PlayerPublicationJobHandler` own admission, immutable snapshots, generated
metadata, resumable uploads, expected-parent commits, tags, and recovery. Do not
reimplement those steps with ad hoc YouTube uploads or Hugging Face commits.

The [entry skill](../SKILL.md) owns prerequisite reads and preview/card routing.
Cards are generated by project code; corrections belong in the renderer or
verified inputs rather than a competing remote README.

## Select the requested outcome

- **Checkpoint Publication:** periodic/final artifacts can be public without
  Acceptance. For a completed direct local-only Run, use
  `gradlab publish-local <run-directory>` to upload its Checkpoints and journal
  and generate public telemetry. It preserves `complete_local`; tracker sync
  is optional and needs its own request. Queued Runs already publish through
  their supervisor; inspect their durable public inventory.
- **Accepted policy Release to Hugging Face and YouTube:** use the player
  publisher below. A bare `$gradlab_upload-checkpoint` request for the combined model
  upload selects this path. It requires an Evaluated Goal enabling HF Release
  and exact verified accepted evaluation evidence. Playback supplies the
  representative replay; it cannot supply Acceptance.
- **Promotion:** determine whether the requested Checkpoint has accepted
  goal-owned evidence and use the owning evaluation workflow. Publication
  cannot confer Promotion. If evaluation is requested, use `$gradlab_launch-experiment`.

A Training-Only or unevaluated Checkpoint remains eligible for Checkpoint
Publication, but cannot enter the accepted-release path. Report a missing
prerequisite or unsupported input rather than bypassing admission or inventing
evidence. Local files must first enter a supported public Run workflow; the
current player publisher admits verified catalog Checkpoints.

## Admit one release

1. Resolve the exact Run and Checkpoint from the public catalog. For local-only
   input, complete its authorized durable artifact Publication first. Open
   `gradlab play --run <run-id>` and select the requested Checkpoint.
2. Capture a representative completed episode and render its replay. Use the
   current episode only; beginning another episode invalidates the old capture
   for a new request. The Policy and evaluation identities must agree.
3. In the player's Publication controls, run credential preflight and preview
   the generated metadata. Confirm the requested privacy and optional editorial
   settings. The code resolves the goal repository, immutable next `vN` tag,
   environment collection/playlist, evidence, and hashes.
4. Admit once and retain the returned job ID and request fingerprint. Reconcile
   a conflict or uncertain response against the existing capture/job before
   submitting again. Authorization to publish the named result permits this
   admission; do not require an extra approval when the request is already clear.

The authenticated player routes are `/api/publication/current`, `/render`,
`/preflight`, `/preview`, `/admit`, and `/jobs/{job_id}` under the same prefix.
Use its existing session controls and authority checks; do not extract or print
session capabilities. `PlayerPublicationService` provides the same operations
for application code. There is no standalone headless HF-release CLI; do not
invent one or substitute `prepare_huggingface_release.py`, which only stages
and validates a bundle.

## Follow and recover

```bash
gradlab jobs show <job-id>
gradlab jobs list --state blocked --state failed
```

Keep following until the admitted job succeeds or reports an evidence-backed
failure requiring action. The worker persists resumable YouTube sessions,
verifies processing while unlisted before HF mutation, commits the exact bundle
and immutable tag, verifies environment containers, and sets final privacy.
Do not upload a duplicate to resolve an uncertain YouTube result. Use the
player's existing-job retry or verified video-ID resolution; cancellation and
cleanup require the corresponding request. Cleanup cannot remove active work.

## Verify and report

Require job `succeeded`, the immutable HF commit/tag and standardized bundle,
the same root `replay.mp4`, successfully processed YouTube video, requested
privacy, verified thumbnail, environment collection/playlist, and cross-links.
Use `scripts/audit_huggingface_release.py <repo-id> --revision <vN>` when an
independent Hub audit is needed. Preserve historical tags and R2 sources.

Report Run/Checkpoint identity, job/fingerprint, HF tag and commit links,
YouTube and environment-container links, and staging/evidence paths. State
Checkpoint Publication and accepted Release outcomes separately.
