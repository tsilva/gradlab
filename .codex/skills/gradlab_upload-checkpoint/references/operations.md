# Upload Checkpoint

Operate the repository's Publication services. `PlayerPublicationService` and
`PlayerPublicationJobHandler` own admission, immutable snapshots, generated
metadata, resumable uploads, expected-parent commits, tags, and recovery. Do not
reimplement those steps with ad hoc YouTube uploads or Hugging Face commits.

The [entry skill](../SKILL.md) owns prerequisite reads and preview/card routing.
Accepted Release cards are generated by project code. Apply corrections to the
renderer or verified inputs.

## Select the requested outcome

- **Checkpoint Publication:** periodic/final artifacts can be public without
  Acceptance. For a completed direct local-only Run, use
  `gradlab publish-local <run-directory>` to upload its Checkpoints and journal
  and generate public telemetry. It preserves `complete_local`; tracker sync
  is optional and needs its own request. Queued Runs already publish through
  their supervisor; inspect their durable public inventory.
- **Selected Checkpoint on Hugging Face:** a separately requested model upload
  includes the replay and game collection steps below. Preserve its Run and
  Checkpoint identity and qualify reported results as training or playback.
- **Accepted policy Release to Hugging Face and YouTube:** use the player
  publisher below. A bare `$gradlab_upload-checkpoint` request for the combined model
  upload selects this path. It requires an Evaluated Goal enabling HF Release
  and exact verified accepted evaluation evidence. Playback supplies the
  representative replay; it cannot supply Acceptance.
- **Promotion:** determine whether the requested Checkpoint has accepted
  goal-owned evidence and use the owning evaluation workflow. Publication
  cannot confer Promotion. If evaluation is requested, use `$gradlab_launch-experiment`.

A Training-Only or unevaluated Checkpoint remains eligible for Checkpoint
Publication, but cannot enter the accepted-release path. Report a missing
prerequisite or unsupported input rather than bypassing admission or inventing
evidence. Local files must first enter a supported public Run workflow; the
current player publisher admits verified catalog Checkpoints.

For a source-overlay Run accepted through `gradlab evaluate-local`, use
`gradlab publish-local <run-directory> --acceptance-queue <private-queue-directory>`
on the host holding the original Run and its private evaluation. This imports
the original checkpoint and recipe bytes and the verified Acceptance evidence.
The import records the original and relocated evidence digests when it moves
the evaluation video into the configured store. A Release still uses the
player's representative capture and the normal Publication controls.

## Publish a model on Hugging Face

1. Resolve the exact Checkpoint, its immutable identity, and the public model
   repository in the approved owner namespace. Ask if the Checkpoint or
   repository is ambiguous. For visual or interactive environments, record a
   representative completed episode in Faithful Playback or reuse a verified
   recording of that Policy under the recorded execution rules. Render it as
   root `replay.mp4` and verify it decodes. Treat the episode as a preview.
2. Stage the complete public bundle. For a selected Checkpoint, use
   `gradlab play 'hf://<owner>/<model-repo>'` in the card's Quick start, with
   any required environment arguments. Use the exact destination and omit
   `@revision` so playback follows the current Hugging Face `main` branch.
   Reject a staged Quick start that uses a pinned revision or an R2 manifest.
   Keep the exact Run and Checkpoint, immutable artifact links, and any R2
   manifest in Provenance. Then record the exact destination, publishable
   filenames and hashes, evidence for the card's claims, and the collection
   addition where applicable. Use the owner's explicit publish request as
   authorization only when the applicable outbound policy permits it. If draft
   review is required or requested, show that exact bundle and await approval.
   Keep ROMs, credentials, and private supporting files out of the upload.
3. Before the first public write, verify the staged bytes and approved transport
   for the whole bundle and applicable collection step. Stop on missing inputs,
   transport gaps, or conflicting destination content. Create or use the exact
   model repository and protect the expected parent on commit. Reconcile an
   uncertain write against the published revision before retrying. Resume a
   collection addition after verifying an exact published bundle match. Never
   write to a legacy redirect target.
   For games, resolve the owner's canonical collection for the environment and
   add the model once. Reuse its verified ID even after an owner-approved rename.
   When creating a collection, default to `Policies - <canonical environment ID>`
   as the title and `Policies that play <canonical environment ID>.` as the
   description. Use owner-specified metadata when provided. Preserve existing
   entries and metadata during ordinary uploads.
   For accepted Releases, the durable publisher owns the collection step.
4. Verify the published files against the staged hashes at the immutable
   revision and confirm the live card. For a selected Checkpoint, verify its
   Quick start uses the unpinned model ID and that GradLab resolves it
   anonymously to the published Checkpoint. Confirm the Video Preview and exact
   game collection membership where applicable. For a game, complete the
   [dashboard update](dashboard.md) for the verified revision. Return the immutable
   revision and public links.

## Admit one release

1. Resolve the exact Run and Checkpoint from the public catalog. For local-only
   input, complete its authorized durable artifact Publication first. Open
   `gradlab play --run <run-id>` and select the requested Checkpoint.
2. Capture a representative completed episode and render its replay. Use the
   current episode only; beginning another episode invalidates the old capture
   for a new request. The Policy and evaluation identities must agree.
3. In the player's Publication controls, run credential preflight and preview
   the generated metadata. Confirm the requested privacy and optional editorial
   settings. The code resolves the goal repository, immutable next `vN` tag,
   environment collection/playlist, evidence, and hashes.
4. After the required public draft approval, admit once and retain the returned
   job ID and request fingerprint. Reconcile a conflict or uncertain response
   against the existing capture/job before submitting again.

The Mario Level 1-3 repository can take its first v4 Release when `main` is
the reviewed legacy checkpoint and `sft-20261102` points to that same commit.
The publisher uses the expected parent for the new commit and leaves the SFT
tag available as the legacy checkpoint's immutable reference.

The authenticated player routes are `/api/publication/current`, `/render`,
`/preflight`, `/preview`, `/admit`, and `/jobs/{job_id}` under the same prefix.
Use its existing session controls and authority checks; do not extract or print
session capabilities. `PlayerPublicationService` provides the same operations
for application code. There is no standalone headless HF-release CLI; do not
invent one or substitute `prepare_huggingface_release.py`, which only stages
and validates a bundle.

## Follow and recover

```bash
gradlab jobs show <job-id>
gradlab jobs list --state blocked --state failed
```

Keep following until the admitted job succeeds or reports an evidence-backed
failure requiring action. The worker persists resumable YouTube sessions,
verifies processing while unlisted before HF mutation, commits the exact bundle
and immutable tag, verifies environment containers, and sets final privacy.
Do not upload a duplicate to resolve an uncertain YouTube result. Use the
player's existing-job retry or verified video-ID resolution; cancellation and
cleanup require the corresponding request. Cleanup cannot remove active work.

## Verify and report

Require job `succeeded`, the immutable HF commit/tag and standardized bundle,
the same root `replay.mp4`, successfully processed YouTube video, requested
privacy, verified thumbnail, environment collection/playlist, and cross-links.
Use `scripts/audit_huggingface_release.py <repo-id> --revision <vN>` when an
independent Hub audit is needed. Preserve historical tags and R2 sources.

Report Run/Checkpoint identity, job/fingerprint, HF tag and commit links,
YouTube and environment-container links, and staging/evidence paths. State
Checkpoint Publication and accepted Release outcomes separately.
